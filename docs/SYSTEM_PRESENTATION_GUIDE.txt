SYSTEM AND SOURCE-CODE PRESENTATION GUIDE
University of Makati
Prepared from the current workspace source tree

======================================================================
1. SYSTEM OVERVIEW
======================================================================

E-Balik is the University of Makati campus lost-and-found system. It
connects students, faculty, staff, and administrators through authenticated
missing-item and found-item reports, matching, claims, custody tracking,
account verification, notifications, and administrative review.

The workspace contains three cooperating applications/services:

	USER WEB APP
		React + TypeScript + Vite + Tailwind CSS
		User-facing pages and responsive mobile/desktop navigation.
		Dev URL: http://localhost:5173

	ADMIN WEB APP
		Separate React + TypeScript + Vite + Tailwind CSS application in Admin/
		Operational dashboard, registries, claim review, users, analytics, logs.
		Dev URL: http://localhost:8443/admin/

	BACKEND API
		Python + Flask, running on http://localhost:5000
		Verifies user/admin JWTs and accesses Supabase with the server-side
		service key.

	DATA AND FILE STORAGE
		Supabase PostgreSQL stores account, report, claim, notification, and
		audit data. Supabase Storage stores item photos, claim evidence, and
		private account-verification documents.

Request/data flow:

	Browser page
			-> frontend API client (Authorization: Bearer <session JWT>)
			-> Flask route (validates token and actor permissions)
			-> Supabase database/storage through backend service client
			-> JSON response back to the page
			-> optional best-effort email through SendGrid

The backend owns identifiers, authorization, persistence, uploads, and
email recipients. The browser does not write directly to Supabase.

======================================================================
3. MAIN USER WORKFLOWS
======================================================================

AUTHENTICATION AND TOKEN FLOW

	1. User registers or logs in through src/app/pages and src/app/utils/api.ts.
	2. Registration verifies OTP before account activation.
	3. Backend returns a JWT; the user client stores it as `ebalik_token`.
	4. Authenticated API requests send `Authorization: Bearer <JWT>`.
	5. Flask verifies the JWT and obtains account_id from its claims. User IDs
		 or email recipients are not   trusted from arbitrary report payloads.

MISSING/FOUND REPORTS

	1. User selects Report Item and chooses a workflow.
	2. FoundItem.tsx or MissingItem.tsx collects form data and optional image.
	3. User API sends multipart FormData; backend validates, uploads supported
		 files, creates the database row, and assigns an MP... or FP... reference.
	4. The backend emails the stored account email with the reference after the
		 database insert. Email is best-effort; the saved report remains valid
		 if SendGrid is unavailable.
	5. My Reports, Dashboard, Matches, and Browse Items reload from APIs.

MATCHING

	backend/app/utils/matching.py compares category, location, date, and text.
	Exact category match adds 30. Location adds 25 for exact, 18 for substring,
	or 10 for shared tokens. Date adds 20 for same-day, 12 within two days,
	or 6 within seven days. Text-token overlap adds up to 25; total is capped
	at 100. User Matches filters use 75% for strong and 55% for possible.
	Admin AI Matching presents candidates from 55% and labels 80%+ high
	confidence. The match is an aid to review, not proof of ownership.

CLAIMS AND APPROVAL EMAIL

	1. Claim.tsx submits a found-item reference, reason, ownership photo, and
		 identity document after a timed review/confirmation step.
	2. backend/app/routes/claims.py verifies the user JWT, validates file types
		 and signatures, stores evidence privately, creates the pending claim,
		 and returns a claim reference.
	3. A receipt email is sent to the claimant's stored account email. It
		 contains the reference and next steps, not claim reason or ID files.
	4. Admin changes a claim to Approved for Pickup in ClaimsVerification.tsx.
	5. After the status RPC commits, Admin loads email/context from the stored
		 claim and sends an approval email. It reminds the claimant to bring
		 original ID; online approval is not final handover.

ACCOUNT VERIFICATION

	Profile.tsx uploads a real multipart file to the private
	account-verification-documents bucket. The database stores its path and
	pending state. Admin Users > Account Verification receives the pending
	request, opens a short-lived signed preview, and approves/rejects it.
	Approval assigns identity category (Student/Faculty/Others), not admin
	privileges. The backend stores the decision and creates a notification.
	App.tsx refreshes shared auth state, so Profile and header state update
	without logout. Notification list and unread badge refresh periodically.

======================================================================
4. ADMIN OPERATIONS AND PRIVILEGES
======================================================================

	Admin login uses the Admin client and `ebalik_admin_token`; API requests
	send it as a Bearer JWT. Backend checks the live user_profiles access level
	and, when configured, MFA verification/session generation.

	`access_level` controls system privilege:
		user         standard account
		admin        operational review and management; no hard-delete rights
		super_admin  elevated management, including protected delete/audit views

	`user_role` is the identity category/program (for example Student or
	Faculty); it is separate from access_level. Account document approval does
	not promote a user to Admin or Superadmin.

	Admin routes include dashboards/reports, item CRUD, matching decisions,
	claim decisions, user status/access management, verification review, MFA,
	and activity logs. Superadmin-only routes enforce privilege server-side.
	Significant admin actions are recorded in user_activity_logs.

	Frontend files: Admin/src/App.tsx, Admin/src/components/Sidebar.tsx,
	Admin/src/pages/*.tsx, Admin/src/utils/api.ts.
	Backend authorization and route implementation: backend/app/routes/admin.py.

5. API ENDPOINT MAP
======================================================================

AUTH: /api/auth
	POST /register, /verify-otp, /login, /google-login
	POST /admin-mfa/verify, /forgot-password, /reset-password
	GET  /profile, /verify-token
	PUT  /profile
	POST /profile/document-upload

FOUND ITEMS: /api/found-items
	POST/GET base route; GET /public, /search, /matches;
	PUT/DELETE /<fpost_id>.

MISSING ITEMS: /api/missing-items
	POST/GET base route; GET /public, /matches;
	PUT/DELETE /<mpost_id>.

CLAIMS: /api/claims
	GET/POST base route; DELETE /<claim_id> (owner's pending claim only).

NOTIFICATIONS: /api/notifications
	GET base route, GET /count/unread, PATCH /<notification_id>/read.

ADMIN: /api/admin
	GET dashboard/reports/items/users/claims/logs/matches.
	POST item creation and AI match decisions.
	PUT/DELETE item references, PATCH user status/access, verification review,
	and claim status. Claim delete and administrator audit view are protected.
	MFA endpoints cover status, setup, verification, and disable.

6. DATA, STORAGE, EMAIL, AND TOKEN SAFETY
======================================================================

MAIN DATABASE TABLES

	user_profiles          identity, contact, role, verification metadata
	otp_tokens             registration and password-reset OTP state
	missing_items          lost-item reports and public references
	found_items            found items, custody, and public references
	claims                 claim owner, reference, status, review timestamps
	ai_matches             persisted match decisions
	user_notifications     user inbox/read state
	user_activity_logs     user/admin activity trail
	claim_change_history   append-only claim change/deletion snapshots
	admin_mfa and related tables
												 TOTP setup, challenges, and recovery codes

STORAGE BUCKETS

	found-item-images and missing-item-images
		Item photos; public listing visibility is constrained by backend fields.
	claim-proof-images and claim-id-documents
		Private claim evidence; backend creates short-lived signed URLs.
	account-verification-documents
		Private user-verification files; Admin previews use signed URLs.

EMAIL

	backend/app/utils/email_service.py sends OTP and reference emails through
	SendGrid. Required server settings: SENDGRID_API_KEY and
	SENDGRID_FROM_EMAIL. Reference emails contain only a report/claim ID,
	status, item name/location details suitable for the owner, and next steps.
	Never include JWTs or OTPs in report/claim emails. OTP delivery for
	registration and password reset is a separate authentication email flow.
	Do not email claim reason, ownership proof, or identity document files.

TOKEN AND SECRET HANDLING

	User JWT: browser key `ebalik_token`.
	Admin JWT: browser key `ebalik_admin_token`.
	JWTs are sent only in the Authorization header to the backend. Never place
	them in email, report references, screenshots, source files, logs, or this
	presentation. The Supabase service-role key, SendGrid API key, JWT secret,
	and encryption key belong only in ignored backend/project environment files
	and must never be put in frontend code or a presentation.

	A JWT identifies an account; backend routes still check current database
	role/ownership. Never accept account_id, claimant email, role, or recipient
	from a public client request when they can be resolved from the token and DB.

8. PRESENTATION DEMONSTRATION FLOW
======================================================================

	1. Show the public landing page and identify the campus lost-and-found goal.
	2. Register/login and describe OTP/JWT authentication at a high level.
	3. Submit a missing report or found item; show its generated reference and
		 explain that the report email is sent after persistence.
	4. Show matching/browsing and explain that public views omit private fields.
	5. Submit a claim with ownership evidence; show the pending state/reference.
	6. In Admin, review the claim and approve it; show the user email, Profile
		 update, notification, and in-person verification next step.
	7. Show Account Verification with a private signed document preview and
		 distinguish identity category from Admin/Superadmin privilege.
	8. Finish with Admin audit/analytics and Auction Hall. Auction Hall is a
		 static design preview: its sample lots are not live data and bidding is
		 disabled.

9. RUN AND VALIDATE
======================================================================

	Start all local services from project root:
		npm run dev

	Or start individually:
		npm run dev:frontend       user frontend, normally :5173
		npm run dev:backend        Flask API, normally :5000
		npm run dev:admin          Admin app, normally :8443

	Production builds:
		npm run build
		npm --prefix Admin run build

	Focused backend checks:
		backend\venv\Scripts\python.exe -m compileall -q backend
		python -m pytest backend\tests\test_claim_status.py

	The repository currently contains one pytest-style claim-status test file;
	pytest is not listed in backend/requirements.txt, so install it in the
	development environment before running that command. Endpoint and live
	Supabase integration coverage is limited.
