## Before production deployment

The repository's Render blueprint deploys `main`. Pushing this feature branch stores the work on GitHub; it does not merge it into `main` or intentionally trigger the production backend. Vercel may create a preview depending on its existing project settings. Review CI through a pull request or manually run its workflow before merging to the production branch.

Deploy the user/admin bundle and Flask backend together. Preserve existing hosted secrets and URLs. Set the hosted `EBALIK_EVENTS_FOUNDATION_ENABLED=true` to make Events available; its default remains closed. Confirm the hosted backend's `PUBLIC_SITE_URL` is the stable public HTTPS user website. Local configuration does not supply that address. `SMART_TAG_TYPES_ENABLED=qr,nfc` permits both issuance media; an explicit `qr` restriction remains honored. `VITE_API_URL` must remain the actual hosted Flask API. Do not deploy the synthetic URL used for offline build verification.

All seven event migration names were verified in the connected project's `migration_log` on 20 November 2026. All 15 event tables have RLS enabled and no direct anon/authenticated table privileges. No new migration is required for NFC or the workspace deletion fix. If deployment targets a different Supabase project, inspect that project's migration state before the user manually applies missing SQL. Do not rerun already-applied files.

Perform real-account acceptance for event access, item/photo intake, claims/release, notifications, closing and custody. Test existing QR scans, one actual NFC write/read-back and optional offline contact on the intended phone/card. Automated checks use mock hardware and cannot certify a physical card.

## Revert the release while retaining history

If this release is the latest application change on the feature branch, with a clean working tree:

```powershell
git switch feature/event-foundation
git pull --ff-only origin feature/event-foundation
git revert release/event-nfc-20261120
git push origin feature/event-foundation
```

This creates a new commit reversing the release. It does not reset branches, force-push, drop tables or delete data. If later commits exist, review conflicts and preserve those changes instead of blindly reverting. If the release was merged into `main`, revert the release on a dedicated rollback branch based on current `main`, review it, then merge that rollback through the normal deployment process. A merge commit may require reverting the merge with the correct parent instead; inspect the actual history first.

To recover service quickly, the hosting dashboards can redeploy the earlier code version identified by `safety/pre-event-nfc-20261120`; both frontend and backend must use compatible versions. Keep the new Supabase tables, buckets, migrations and recovery records. A source-code rollback does not reverse SQL or erase offline contact written onto physical NFC cards. Older code will not expose the new event interfaces; retain an operational plan for any items already in event custody.

Do not execute database rollback/drop scripts as part of this code revert. Existing campus tables and income records stay intact. Owner contact already encoded on a card requires physical rewriting to change.
