## Entry 1 — System polish, bug fixes and logic refinements (claims, reports, privacy, notifications, auctions)

### Prompt Audit
**System Polish, Bug Fixes & Logic Refinements.** Read `CLAUDE.md`. Do not push to git when finished; the user tests locally first.

**Phase 1: Critical workflow fixes**
1. Claim duplication bug: submitting a claim creates multiple records with different IDs. Make one submission produce exactly one unique claim record.
2. Report redirection: after a successful Missing or Found report, redirect to "My Reports" and visually highlight the new report.
3. Verification state delay: when an admin approves a user's verification, "My Profile" does not update until the user logs out and back in. Fix the state management or polling.

**Phase 2: Anti-spam, privacy and notifications**
1. Add a required Data Privacy Act consent checkbox to the Missing, Found, Claim and Verification forms and modals.
2. Limit each account to 3 active reports, and add a basic description-matching check against duplicate or highly similar reports. Notify the user with a modal for both.
3. When an admin confirms an AI Match, automatically email the affected user.

**Phase 3: Auction and comment overhaul**
1. Foul-word filter for auction comments: block the submission and show a modal about the violation.
2. Anonymise bidders on user-facing auction pages (for example "Bidder_8X9").
3. Fix the auction flow: Re-Auction only after confirming a winner; users can see bidding history and logs on the auction page; save auction reactors (users who liked or watched); properly trigger the winner email when an auction is won.

**Rules:** surgical edits, do not break existing features, keep Admin and User consistent, log prompt, edits and database changes here.

### Findings (root causes)
- **Claim duplicates:** `Claim.tsx` `confirmSubmission` had no in-flight guard, and `createClaim` (unlike the report calls) never sets the shared `isLoading` flag, so the Confirm button stayed enabled while the request ran. A double-click sent two requests. The backend "already pending?" check then raced: both requests passed it before either insert committed. No database constraint existed. The same race applied to the found and missing report forms.
- **Verification delay:** every `useAuth()` call has its own state, the Profile page rendered a copy of the user that nothing refreshed while it was open, and the app-wide poll ran only every 20 seconds (and only updated its own copy).
- **Winner email:** the default mode was `mock` (log only), `render.yaml` forced it, and a failed send was never recorded, so a failure was invisible and could not be retried.
- **Re-auction** was allowed straight from "awaiting admin", before a winner existed.
- **Hearts** were stored in the browser only, so the admin could not see them.
- Public auction pages showed "first name plus last initial" (for example "Maria S.").
