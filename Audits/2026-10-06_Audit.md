### Findings (root causes)
- **Claim duplicates:** `Claim.tsx` `confirmSubmission` had no in-flight guard, and `createClaim` (unlike the report calls) never sets the shared `isLoading` flag, so the Confirm button stayed enabled while the request ran. A double-click sent two requests. The backend "already pending?" check then raced: both requests passed it before either insert committed. No database constraint existed. The same race applied to the found and missing report forms.
- **Verification delay:** every `useAuth()` call has its own state, the Profile page rendered a copy of the user that nothing refreshed while it was open, and the app-wide poll ran only every 20 seconds (and only updated its own copy).
- **Winner email:** the default mode was `mock` (log only), `render.yaml` forced it, and a failed send was never recorded, so a failure was invisible and could not be retried.
- **Re-auction** was allowed straight from "awaiting admin", before a winner existed.
- **Hearts** were stored in the browser only, so the admin could not see them.
- Public auction pages showed "first name plus last initial" (for example "Maria S.").

### Design decisions
- `tag_id` is 12 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0/O/1/I, so a code read off a sticker cannot be mistaken), chosen with `secrets.choice` (about 60 bits), generated by the backend rather than in SQL so it uses the operating system's secure RNG without needing a database extension. The table CHECK enforces only the format.
- The phone number lives on the tag (`contact_phone`), not on the profile, because user profiles have no phone field; `show_phone` requires one.
- "Ban" is a separate `is_disabled` flag (with reason, actor and time) rather than a fourth status, because the spec fixes the status set to blank, active and lost and a ban must be reversible without losing the owner's lost/active state.
- Privacy defaults: name and email on, phone off in the form; every column defaults to off in the database. The form shows a live preview of exactly what a finder will see.

### Security review
- **Enumeration:** about 60 bits of entropy, a uniform 404 for unknown codes, and 90 lookups per minute per address.
- **Data exposure:** `public_view` is an allow-list, so no database column reaches a finder unless named; toggles are tested in all 8 combinations; blank, disabled and ownerless tags reveal nothing; another owner's tag answers 404 exactly like a missing one; responses are `no-store` and `noindex`.
- **Races:** claiming is one conditional UPDATE (blank, unowned, not disabled), so two simultaneous claims cannot both win; the owner alert is claimed atomically so simultaneous finders send one message.
- **Abuse:** finder notices are rate limited per address and per tag, with a 5 minute per-tag cooldown; the finder always still receives the guard post instructions; super admin can deactivate a tag instantly; an account can hold at most 25 tags. The client address comes from the last `X-Forwarded-For` entry (the one Render adds), which a caller cannot spoof.
- **XSS and injection:** text is stripped of angle brackets and control characters on the way in, rendered only as React text, escaped in emails; `mailto:` and `tel:` links are created only for values matching a strict pattern. A hostile item name, description, name, email and phone were rendered in the browser: no element was created, no link was generated and no script ran.
- **Consent:** registering a tag requires Data Privacy Act consent, enforced by the server (400 `dpa_required`).
